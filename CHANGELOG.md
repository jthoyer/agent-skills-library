# Agents CHANGELOG

The improvement ledger for this agent library. Every review by `agent-improver` appends a dated entry here. The goal: agents that are measurably better in three months than they are today.

**How to read this:** each entry records what changed, why, and how you'd know it worked. Before re-reviewing an agent, read its most recent entry and check whether the last fix actually helped.

**Entry format:**

```
## YYYY-MM-DD — <agent name>
- Verdict: <one line>
- Changed: <what was edited, or "no edits — proposed N fixes">
- Why: <root cause>
- Expected effect: <what should improve, and how you'd know>
- Follow-up: <deferred items or items needing sign-off>
```

## 2026-09-05 — `cody` + `mc-verifier` + `release-engineer` (lessons from this session's test-building work applied)
- Verdict: **REDUCED INDEPENDENCE — direct edits, no `agent-improver` dispatch.** Three edits, each traced to a specific, freshly-observed incident in this same session (not a general review) — the kind of finding the library's own norm treats as safe to apply directly and flag for later independent check, same pattern as the earlier 2026-09-05 backlog sweep.
- Trigger: this session built the first-ever test suites for two apps (Balance Bolt, Tri Momentum) and hit two real, reusable lessons — one a testing-craft mistake caught in the act, one an environment hazard that cost several failed workarounds before it was correctly diagnosed. User then asked to "upgrade agents as a result of above."
- **1. `cody.md` — a tautological test assertion, and how to catch one.** Writing Balance Bolt's suite, one check compared `groupByPredicted()`'s wave count to `MAX_WAVES` — the same constant the code under test defines — so changing `MAX_WAVES` from 4 to 5 to deliberately break the suite left it passing all 74 checks anyway. Added to §1: when writing tests for previously-untested code, deliberately break one enforced fact and confirm the suite goes red before trusting a green run, and pin literal values rather than asserting a constant against itself. Also added a Behaviours-to-avoid bullet for item 3 below (cody has `Bash` and may run git to check its own scope).
- **2. `mc-verifier.md` — the same lesson from the Verifier's side.** Its entire mandate is confirming code by running it, which makes it the natural place to require confirming a *newly written* suite can fail, not just that it currently passes — a green run of an untested suite is not yet evidence of anything. Added as a Behaviours-to-adopt bullet, distinct from the existing coverage check (this asks whether the tests that exist test anything at all, not whether the right things are tested).
- **3. `release-engineer.md` — a cloud-sync git hazard, diagnosed the hard way.** Committing Tri Momentum (hosted in a Google-Drive-synced folder) failed: `git log`, `git status`, `git commit`, and even plain `cp -R .git` all errored `mmap failed` / `fcopyfile failed: Operation timed out`, while `git add` and `git hash-object -w` (writing brand-new small files) succeeded. Several increasingly invasive workarounds were attempted (copying `.git` to scratch, rsync) before stopping to diagnose and ask, which is the wrong order — this should have been recognised and escalated on the first failure. Added to step 1: recognise the failure signature, do not retry-loop (confirmed non-transient: a failing `git commit` given up to 9 minutes still failed in 0.07 seconds), do not attempt filesystem-level workarounds without asking, and name the likely cause (Google Drive/Dropbox/OneDrive) so the user can decide whether to relocate the working tree. Matching Behaviours-to-avoid bullet added.
- Why these together: both are transferable craft lessons this library had no record of before today, each cheap to encode and each already cost real time once. Grouped as one entry because all three edits trace to the same one session's work, not three independent reviews.
- Expected effect, falsifiable next run: a `cody`/`mc-implementer` dispatch that writes tests for untested code reports a deliberate break-and-restore rather than just a green run; `mc-verifier` states the same when handed a new suite to verify; `release-engineer` (or `cody`, informally) recognises an mmap/fcopyfile failure on sight and asks before improvising, rather than retrying or copying `.git`.
