**Do not add passwords. Add an approval queue to the sign-in you already have.**

A new person signs in with their email and a 6-digit code, as today. They then give a display name and a short note. You get an email. You approve or reject them in the admin console. Approval adds them to the allow-list that already guards every write. Nothing else in the security model changes.

## SCR summary

**Situation.** The app already gates writes. People sign in with a one-time email code (`signInWithOtp`, `app.js:324`). Only addresses on a hashed allow-list can write (`private.is_allow_listed()`, migration `20260924050902`). You run an admin console with two-factor sign-in, a 30-day activity feed and a per-change **Undo** (`20260924054526`). Every write to `entries` and `races` is copied to `private.change_history`.

**Complication.** Approval today is invisible and manual. Someone who is not on the list signs in, gets bounced with "email mail@balancetriclub.com" (`app.js:193-201`), and you must type their address into the allow-list panel by hand (`admin.js:678`). You get no notice. They see no "pending" state. Nothing records who asked, who decided, or why. Your ask for "username and password" signup would solve the notice problem. But it would also add password storage, resets and reuse risk, and remove nothing.

**Resolution.** Keep passwordless sign-in. Add a request-access step, an admin email per request, and an approve/reject queue in the console. Approval writes to the existing allow-list, so every existing RLS policy keeps working unchanged. Three reasons:

1. **It is safer.** An email code proves inbox ownership on every sign-in. A password proves it once, then becomes a reusable secret members recycle from other sites.
2. **It is smaller.** Four of the six capabilities you asked for already ship (verified email, gated writes, admin console, reversible changes). The new work is a queue, a notification and two screens. Estimate: 4 to 5 days.
3. **It fits how members join.** Most club members are already known to the club. A roster fast lane lets them in without your involvement. The queue only handles exceptions.

**Decision needed from you:** approve the recommended design (A + roster fast lane), and answer Q2 and Q3 below.

## 3. Users

- **New member.** Has a club relationship. Wants to commit to a race in under two minutes.
- **Existing member.** Already on the allow-list. Must notice nothing.

## 4. Solution overview

```
 NEW PERSON                        DATABASE / SERVER                     ADMIN (you)
 ----------                        -----------------                     -----------
 Opens app, taps "Sign in"
 Enters email ------------------>  Auth sends 6-digit code (+ link)
 Types code ------------------->   Email confirmed; profile row created
                                   is_allow_listed()?
                                     yes -> full member (no change from today)
                                     no  -> my_access_status() = 'none'
 Sees "Request access" sheet
 Display name + note ---------->   request_access()  -> access_requests
                                   status = 'pending'
                                   trigger -> pg_net -> Edge Function
                                                     -> email to admin ----> "New request: Sam Lee"
 Sees "Waiting for approval"                                                Opens admin.html
 (can browse, cannot write)                                                 Two-factor sign-in
                                                                            Requests panel
                                   admin_decide_request(id, 'approve') <--- Approve
                                     -> hash added to allowed_emails
                                     -> admin_actions row
 Next load: member, can commit
 Commits to a race ------------>   entries insert (RLS: is_allow_listed)
                                   change_history row (who, old, new)
                                   admin_undo(change_id) <------------------ Undo (any time)

 Reject  -> status 'rejected', not on list, signed out with a message, cannot re-request
 Revoke  -> hash removed, status 'revoked', writes blocked at once, entries kept
 Re-approve -> hash re-added, status 'approved', logged
```

**Design rule.** The allow-list stays the **only** gate that RLS checks. `access_requests` is the workflow and the record. It never grants anything by itself. This keeps one source of truth for "can write".

### 5.4 Race flow and reversal

The race flow itself does not change. What changes is who gets to it.

1. Person signs in and is approved (5.1 to 5.3).
2. They open a race and commit. Their display name fills "Your name" (`app.js:233`).
3. `entries` insert passes RLS because `is_allow_listed()` is true. `created_by` is stamped by trigger.
4. `change_history` records the insert: old row, new row, `changed_by`, role, time.
5. Edits and removals follow the same path.
6. You reverse any single change from **Activity → Undo** (`admin_undo`). Undo refuses if a later change touched the row, so you never wipe someone's newer edit.

| ID | Requirement | Priority |
|---|---|---|
| R1 | Keep the honour system: an approved member may edit any entry. The README records why ownership is not enforced. Revisit only after an incident. | Must |
| R2 | Activity panel gets a **member filter**: "Show changes by <person>". Makes "reverse everything this person did" a short task. | Should |
| R3 | **Undo all by member** (last N days, newest first, stops at the first conflict). | Could (phase 2) |
| R4 | Extend Activity history beyond 30 days with a date picker. Data is already kept. | Could |

## 6. Data and security

### 6.1 New table

```
private.access_requests
  user_id        uuid primary key references auth.users on delete cascade
  display_name   text not null  (2..40, checked)
  note           text           (<= 280, checked)
  status         text not null  check in ('pending','approved','rejected','revoked')
  requested_at   timestamptz not null default now()
  decided_by     uuid references auth.users on delete set null
  decided_at     timestamptz
  reason         text           (<= 200, admin-only)
  notified_at    timestamptz    (set when the admin email succeeds)
```

RLS on, no policies, all grants revoked. Same pattern as `private.allowed_emails`. One row per user (primary key) is the duplicate-request guard.

### 6.2 New functions

All `security definer`, `set search_path = ''`, `execute` revoked from `public, anon`, granted to `authenticated`. Same pattern as `20260924054526`.

| Function | Caller | Does |
|---|---|---|
| `public.my_access_status()` | Any signed-in user | Returns the caller's own state only (`none`, `pending`, `approved`, `rejected`, `revoked`). Takes no arguments, so it cannot probe other addresses. |
| `public.request_access(p_display_name, p_note)` | Signed-in, confirmed, not listed, no existing row | Validates, checks name uniqueness, writes `profiles.display_name`, inserts `pending`. |
| `public.admin_requests(p_status)` | Admin | Lists requests with email from `auth.users`. |
| `public.admin_decide_request(p_user_id, p_decision, p_reason)` | Admin | `approve`, `reject`, `revoke`, `reapprove`. Updates allow-list and request row, logs to `admin_actions`, all in one transaction. |

Every admin function starts with `perform private.require_admin()`, which checks `private.admins` and the session's `aal2` claim.

### 6.3 How the admin role is enforced

- Admins are rows in `private.admins`. The browser cannot set or read that table.
- The console never touches a table. It calls `public.admin_*` functions, each of which calls `require_admin()`.
- Two-factor is required by default (`mfa_required = true`).
- `isAdmin` in `app.js:175` only shows a link. It grants nothing.

No change is needed here. The new functions reuse it.

### 6.4 The email trigger

1. `after insert` trigger on `private.access_requests` calls `net.http_post` (pg_net) to an Edge Function `notify-access-request`. It sends only the `user_id`.
2. The trigger adds a shared secret header read from Vault. The Edge Function rejects calls without it, so the public key cannot make it send mail.
3. The Edge Function re-reads the request with the service role and builds the email itself. It never trusts payload text. The recipient is a fixed Edge secret, not a parameter.
4. It sends through Resend (or the same provider you pick for Q2), from a verified `balancetriclub.com.au` sender, then sets `notified_at`.
5. Cap: at most 20 admin emails per Sydney day. After that, one "N more requests waiting" email at 8 pm. Protects your inbox and the provider quota from a bot wave.
6. If the send fails, `notified_at` stays null. The console shows "email not sent" so you still see the request.

A Supabase Database Webhook does the same job with less code, if it supports the `private` schema on this project. Check during build.

## 8. Better option? Alternatives compared

| Option | How it works | Security | Admin effort | Member effort | Build | Verdict |
|---|---|---|---|---|---|---|
| **A. Approval queue on passwordless sign-in** (recommended) | Email code, then request, admin approves in console | Strong. Inbox proven every sign-in. No password to leak. | One tap per stranger | Email + code, then wait | 4 to 5 days | **Best core** |
| **B. Club-roster allow-list** | Load member emails from JustGo. Listed people are in at once. | Strong, if the roster is current | Upload a roster each season | Lowest. No wait. | 1 to 2 days (bulk add) | **Add as phase 2 fast lane** |
| **C. Invite codes** | Admin issues a code. Code unlocks access. | Weak if shared. A club-wide code leaks in a group chat. Per-person codes need you to know the email first, which is B with extra steps. | High | Must find and type a code | 2 to 3 days | Reject |
| **D. Email + password + approval** (your ask) | Supabase `signUp` with password, confirm email, then the same queue | Weaker. Password reuse, credential stuffing, reset flow to secure. Leaked-password checking needs a paid Supabase plan (Pro, per Supabase docs). | Same as A | Remember a password. Reset when forgotten. | 6 to 7 days | Not now |
| **E. Google / Apple sign-in + approval** | Social login, then the same queue | Strong | Same as A | Fastest sign-in | 2 to 3 days extra, plus provider setup | Optional later |

**Why not your design as written.** It is close. The approval in the admin section, the email to you, and reversible submissions are all right and all kept. Two parts change:

- **"Username and password" becomes "email code".** You already need an email to verify the person. Once you send an email, a code is the credential. A password adds a second secret that is weaker than the first.
- **"Username" becomes "display name".** Email is the login identifier. Display name is what the club sees. A separate username adds a third thing to remember and protects nothing.

**If you still want passwords (option D), spec it like this.** Minimum 12 characters, no composition rules (current NIST guidance favours length over symbols), reject the 1,000 most common passwords client-side, Supabase `minimum_password_length = 12`, `secure_password_change = true`, leaked-password protection on (needs Pro). Add a "Forgot password" flow with the branded `recovery` template. Keep the email-code option alongside, so nobody is locked out.
