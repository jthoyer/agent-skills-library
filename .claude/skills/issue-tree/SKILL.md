# Issue Tree

Structured problem decomposition using the McKinsey-originated Issue Tree method, adapted for service design, operational analysis, and executive problem-solving.

---

## What an Issue Tree Is

An Issue Tree is a **MECE map of a problem** — it covers the whole problem space with no gaps (Collectively Exhaustive) and no overlaps (Mutually Exclusive).

It enables three things:
1. **Map** — a clear, rigorous view of the problem's full structure
2. **Divide and conquer** — break the problem into independently workable parts
3. **Prioritise** — identify where to focus investigation before committing to analysis

---

## Two Types of Issue Tree

| Type | Also called | Use when |
|------|-------------|----------|
| **Why Tree** | Problem Tree / Hypothesis Tree | You have a problem and need to find its root cause |
| **How Tree** | Solution Tree | You want to generate structured options to fix or improve something |

The most powerful combination: use a Why Tree to find the problem, then a How Tree on the confirmed root cause.

---

## Three Techniques to Build an Issue Tree

### Technique 1 — Math Tree (numerical problems)

Break down the target metric using equations. Math is always MECE.

**Four methods:**
1. **Proven formula** — use known relationships (Profit = Revenue − Cost; Market Share = Our Volume / Total Volume)
2. **Dimensional analysis** — pick one direct driver, then find its mathematical complement (Revenue = Customers × Revenue per Customer)
3. **Funnel method** — multiply the stages of a conversion funnel (Conversion Rate = % who view × % who click × % who buy)
4. **Sum of segments** — split by meaningful segment (Revenue = Product A + Product B + Product C)

Use math as long as it remains **meaningful and insightful**. When the equation stops adding insight, switch to Technique 2 for deeper layers.

---

### Technique 2 — Layering MECE Structures (qualitative or mixed problems)

Layer "mini MECE structures" on top of each other, one bucket at a time.

**The five ways to be MECE** (apply one per layer):
1. **Algebra structure** — mathematical relationship between parts
2. **Process structure** — sequential steps (input → process → output; or funnel stages)
3. **Segmentation** — divide by a meaningful dimension (customer type, geography, product line, channel)
4. **Conceptual framework** — organising principle from theory (supply vs. demand; internal vs. external; short vs. long term)
5. **Opposite words** — mutually exclusive binary split (voluntary vs. involuntary; controllable vs. uncontrollable)

**Process:**
1. Define the problem specifically — what exactly are you trying to explain or solve?
2. Break into a first layer using the most relevant MECE structure
3. For each bucket, choose the best MECE structure for that sub-problem
4. Repeat until each bucket can *reasonably* explain or resolve the issue

---

### Technique 3 — Decision Tree (conditional logic)

Adds IF-THEN logic to regular Issue Trees. Use when the path forward depends on what you find at each node.

Example: *If* demand is the constraint → focus on customer acquisition. *If* capacity is the constraint → focus on operational expansion.

Decision Trees are advanced. Master Techniques 1 and 2 first.

## Six Principles for Quality Issue Trees

**1. Separate different problems early**
If there are two fundamentally different root causes, split them at the first layer. Don't try to solve them together.

**2. Build one layer at a time**
Don't try to see the whole tree at once. Define the problem → build Layer 1 → build Layer 2 for each bucket. One bite at a time.

**3. Every part must be MECE**
No gaps, no overlaps. Use the five MECE structures as a checklist. Aim for "as MECE as possible" — perfection is rare, but gaps at Layer 1 are fatal.

**4. Every part must add insight**
There are many MECE ways to break down a problem. Choose the one that is *problem-specific* and *relevant* — not just technically correct. Generic structures ("Stage 1, Stage 2, Stage 3") add no insight.

**5. Every part should be eliminative (falsifiable)**
Build buckets you can *test*. If data rules out a branch, you can eliminate it and focus. Buckets that cannot be tested or disproved slow down the analysis. When falsifiability is impossible, maximise insight instead (Principle 4).

**6. Clarify before building each layer**
Ask questions to understand what you're breaking down before you break it. Don't guess when you can clarify.

---

## How Deep to Go

- Stop each branch when the bucket can **reasonably explain the problem** — i.e., when a well-informed person would accept it as sufficient.
- If the bucket still raises the question "but *why*?" from a reasonable person, go a layer deeper.
- Typical range: **2–5 layers**. Less than 2 is not structuring; more than 5 rarely adds value in most contexts.
- You do not need to stop all branches at the same depth — go deeper where the problem actually is.

## Common Mistakes to Avoid

| Mistake | What it looks like | Fix |
|---------|-------------------|-----|
| **Wrong problem definition** | Tree maps a broader or different problem than the one stated | Re-read the question; define the specific variable you are decomposing |
| **UnMECE first layer** | Overlapping or incomplete top-level buckets | This is fatal — rebuild using one of the five MECE structures |
| **Irrelevant segmentation early** | Geographical or demographic split as Layer 1 when it is not a key driver | Put segmentation as a side-note or later layer; lead with causal structure |
| **Aggregator fallacy** | Treating a container (e.g. number of warehouses) as a cause of the problem | Only use causal drivers — things that *cause* the metric to change |
| **Solutions before root cause** | Jumping to how-to-fix before you know what is broken | Finish the Why Tree first; build the How Tree on the confirmed root cause |
| **Missing the value dimension** | Structuring only volume when value may be the actual problem | Always check: is the issue count, value, or both? |

## Output Structure

When applying the Issue Tree skill, produce output in this sequence:

**1. Problem definition**
State specifically what is being decomposed — the metric, question, or decision. Clarify scope, timeframe, and relevant context.

**2. Tree type**
Confirm: Why Tree (root cause) or How Tree (solutions). State which technique(s) will be used.

**3. Issue Tree**
Present layers clearly. Use indentation or a labelled hierarchy. Show which MECE structure is used at each layer.

**4. Prioritisation notes**
Flag which branches are most likely to explain the problem (or most impactful to fix), based on logic and any available data.

**5. Recommended next steps**
Which branch(es) to investigate first, and what data or analysis would allow a branch to be eliminated or confirmed.

**6. Open questions**
What would you clarify before proceeding, and what assumptions are embedded in the structure?

## Quick Reference: Technique Selection

| Problem type | Start with |
|-------------|-----------|
| Numerical metric has changed | Technique 1 (Math Tree), then Technique 2 for deeper layers |
| Qualitative or mixed problem | Technique 2 (layering MECE structures) |
| Decision with conditional paths | Technique 3 (Decision Tree) |
| Generating solution options | How Tree using Technique 2 |
| Diagnosing root cause | Why Tree using Technique 1 or 2 |

## Application in icare / Service Design Context

Issue Trees are directly applicable to:

- **Scheme performance problems** — why has claim duration increased? why are service expectation scores dropping?
- **Cost driver analysis** — decompose scheme costs into controllable and structural components
- **Solution design** — what are the MECE categories of intervention to improve participant experience?
- **KPI design** — break down a scheme goal into measurable sub-components and track each
- **Presentation structure** — use the tree as the backbone of an executive briefing (see Bonus Chapter application)
- **Research briefs** — use a Why Tree to scope a research question into investigable sub-questions

When building icare issue trees, always apply The Playbook confidence-grading discipline from the relevant scheme skill:
- **Confirmed** — supported by published data or legislation
- **Inferred** — logical given what is known
- **Asserted** — hypothesis requiring investigation
