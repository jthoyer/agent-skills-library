The necessity test — the principle behind every verdict below

An agent has to earn a separate process. A skill does not. A skill is instructions loaded into the current turn: no cold start, no context reload, no dispatch, and it inherits whatever tools the thread already holds. An agent is a subagent with its own context window and its own declared tool set. Everything an agent can do that a skill cannot comes from exactly one of those two differences — plus the third thing they combine to allow, which is running two of them at once.

So the test, applied to all twenty agents that existed the morning of 2026-08-18, is a single question:

The test

Does this agent’s job require something a skill structurally cannot provide? Namely: (1) a separate context window — the work reads or generates so much that the main thread wants only the conclusion, or the work must be graded by something that never saw it produced; (2) an isolated tool set — the role is defined by what it cannot do, and in-thread that is an instruction rather than a guarantee; or (3) genuine concurrent dispatch, where two actors run without either anchoring on the other’s output.

If yes → KEEP, with the specific structural reason named. If the job is bounded, single-pass, and a skill loaded into the main thread would do it just as well → RETIRE, naming the skill that replaces it. Nine failed, and are documented in v2. This edition (v3) makes no further retirement — it adds a capability to two of the eleven survivors instead.

Not a cost exercise

Nothing here was retired for being long, duplicative or unloved. Every verdict cites a structural property or its absence, and the two retirements that did destroy a real tool guarantee say so in those words.

Retirement is reversible; that is the point

All nine were archived unmodified under ~/.claude/skills/_retired/, each with a _superseded-by.md pointer and a stated reversal condition. There is no git behind ~/.claude — the archive move is the undo, and there is only one.

The finding that decided v2 — now partially resolved

Verified on disk 2026-08-18 · corrects v1

Not one of the twenty agent files declared an Agent or Task tool at the time v2 was written. A subagent receives exactly the tools its own tools: line grants, so neither orchestrator could dispatch its own actors — the concurrent Stage 2 pair (Devil’s Advocate + Subject Matter Validator) and the concurrent Stage 3 pair (Reviewer + Verifier) could not fire from the orchestrator that was supposed to coordinate them, in any environment, ever.

v1 asked to have this verified rather than taken on faith, and it did not survive. The previous edition concluded that “the twelve pipeline actor files earn their maintenance” and that the concurrency was “a real capability rather than a documented aspiration.” The first half stands in a narrower form — a restricted-tool actor can be dispatched as a genuine cold context, which is what the five surviving mc-* actors rest on. The second half did not, until later the same day.

Resolved 2026-08-18, later the same day — at direct user instruction

Agent was added to both mc-orchestrator.md’s and prody.md’s tools: lines. This was the single cheapest unfixed defect v2 named — one line converting five actor files from unusable-as-designed to usable-as-designed. mc-orchestrator can now dispatch its own actors, including the real concurrent mc-reviewer/mc-verifier pair, when it is itself run as a genuine subagent rather than embodied. prody can now genuinely delegate rather than only embody.

What this does not resolve: having Agent in the tools: line is necessary but not sufficient. Dispatch reachability is still a per-session fact — a session with no Agent/Task tool available at all still forces embodiment, regardless of what any file declares. The next time either agent runs, its own step-0 dispatch probe is still the only thing that tells you which case you’re in — don’t read this fix as “concurrency now always works.”

Inline self-review — the review moves earlier

Every review in this library so far has run after the work was handed back — pipeline actors checking each other’s stage output, or prody’s step-5 close-the-loop running once everything is already done. As of 2026-08-18, two agents can pull in a second, different check on their own output before they return it as final. This is not a blanket capability applied to all eleven — it was scoped to the two agents that actually lacked a review step and where a skill was structurally sufficient, after an initial broader-scope proposal was deliberately narrowed.

The rule that had to hold

This library already states, in its own v1 diagram caption: no actor grades its own work. Both routes above go to a skill, never to the agent calling itself — a skill is not the same party as the agent invoking it, and neither addition needed a new Agent tool grant.

Skill before agent, again

Consistent with the necessity audit’s own principle: reach for a skill before spawning an agent. Both code-review and red-team load into the calling agent’s own turn — no cold start, no dispatch tool required. That is also why only these two got this, not all eleven: most of the other nine are either already checked by something else in their own pipeline (mc-implementer), or are themselves the checking mechanism (mc-reviewer, mc-verifier, mc-integrator, watchdog, agent-improver, code-improver), or the addition wasn’t evidenced as needed (prody).

What this doesn’t replace

Step 5 still runs, unchanged. code-review/red-team here check the immediate output before it’s returned; watchdog checks the delivered artifact against the rest of the codebase for duplication and drift; agent-improver grades the agent itself across runs, not a single output. Three different questions — an inline pass answers only the first, and doesn’t excuse skipping the other two when the work is consequential.

The loop

One door, with an exception

Calling an agent by name works and skips the framing — prody’s own rule is to stay quiet when you’ve already chosen. What you skip is the closing review, which is the part that compounds.

Climb only as far as needed

Inline is the default rung; a single specialist is the next; the pipeline is for work that will be merged or shipped. A skill is not a rung on that ladder — it costs no cold start, so reaching for multi-actor-research is cheaper than reaching for cody. Inline self-review is smaller still: it happens inside a rung that was already climbed, not a new one.

Two graders, two subjects

agent-improver grades the agent that did the work. watchdog grades the work itself for duplication and drift. Running only one leaves the other gap uncovered — and neither is replaced by cody or mc-planner checking their own output first.

Inside the one remaining pipeline

Which model each agent runs on

The tier tracks what the agent produces that nothing downstream checks. Not seniority, not how important the agent feels. If a later actor grades the work against something fixed — a spec, a rubric, a test suite — the work is bounded and sonnet is the right call. If the agent’s output becomes the thing everything else is measured against, or if it arbitrates between other agents, an error there is invisible to every check that follows, and that is what opus is for.

Unchanged this edition: 7 of 11 on opus. Adding inline self-review didn’t move any tier — cody and mc-planner route to skills that inherit the calling agent’s own tier, the same limitation v2 already named for every skill in this library: a skill cannot carry a model tier independent of its caller.

opus — nothing checks it

Framing, arbitration at impasse, adversarial static reading, composition, and any grading pass. The hub, the orchestrator, both graders, and the three mc-* actors holding decision or spec rights.

sonnet — a downstream actor checks it

Implementation against an approved spec (cody, mc-implementer), execution and reporting (mc-verifier), and read-only passes that cannot edit (code-improver).

The tier a skill cannot hold

cody’s inline code-review pass runs at whatever tier dispatched cody — sonnet, same as always. That is a known, accepted limitation, not an oversight: the alternative was a new Agent grant to spawn a separate-tier reviewer, which the scoped-down design deliberately avoided.

The arrows, revisited

v1 said “settled 2026-08-16” · v2 corrected it · v3 records the fix landing

What v1 got right, and both later editions keep: independent dispatch genuinely executes. A dispatched agent-improver reviewed prody’s portfolio section and reported, unprompted, that it could see no conversation prior to its brief — then found eight problems, two confirmed by measurement. That is the foundation the five surviving mc-* actors stand on.

What v1 got wrong, and v2 found: not one agent file declared an Agent/Task tool, so no orchestrator could ever dispatch its own actors — the concurrency v1 called “a real capability” was a documented aspiration.

What v3 adds: the fix shipped the same day v2 named it, at direct user instruction, to exactly two files (mc-orchestrator.md, prody.md) rather than blanket-applied. The general lesson v2 drew still holds and is worth restating rather than assuming solved: frontmatter is the ground truth for every capability claim made anywhere in this library, and the fix here was one line per file, not a redesign. The next time this library claims an agent can or cannot do something, the check is a grep '^tools:' away — cheaper than the paragraph explaining why it matters.
